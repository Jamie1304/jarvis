# JARVIS v1.0.0 release candidate

This document describes the intended v1.0.0 candidate. It is not a publication
notice and does not authorize release by itself.

## Product philosophy

JARVIS is a minimal adaptive core that grows its capabilities through use. It
does not ship as a large catalog of product-specific integrations. Normal new
capabilities are discovered, adopted or reused where safe, and built only when
necessary through the controlled acquisition pipeline.

## Fresh install

A fresh installation provides the generic application/runtime foundation:

- durable PlanningEngine tasks and GoalSupervisor intent;
- bounded agent/provider/session/context primitives;
- trusted permission, audit, credential-reference and recovery boundaries;
- generic computer, filesystem, process, browser-semantic, voice, audio,
  camera, vision, artifact and presentation contracts;
- capability discovery, package review/certification, sandbox brokers,
  lifecycle staging, verification, health/drift and repair services;
- memory, User Model, approved-source Knowledge Libraries, Skills,
  WorkflowTemplates, Event Automation, AttentionPolicy, ResourceGovernor and
  Golden Workflow controls;
- production-owned TestDrive registry, setup/adoption contracts, encrypted
  backup/migration and human-readable execution trace services. The optional
  `FirstRunWizard` adapter is not a claim that a fresh desktop bootstrap has
  completed onboarding automatically.

Optional hardware and external companions are unavailable until explicitly
configured and supported. A missing optional backend never becomes an
uncontrolled fallback.

## Self-expansion

The application-owned flow is:

```text
discover -> adopt/reuse -> research -> build -> sandbox -> certify
          -> Shadow -> Canary -> Active -> verify -> persist/repair
```

Discovery is evidence only. SetupContext does not grant authority. Generated
packages cannot write certification evidence, activate themselves, promote
themselves, or enter Trusted Core. Real effects remain behind:

```text
Tool -> PermissionBroker -> Policy -> trusted approval when required -> execution
```

## Security

PermissionBroker is the authority boundary for privileged operations. Trusted
application code owns permission narration, exact operation fingerprints,
approval expiry and consumption. Model text, events, page content, package
metadata and generated UI cannot impersonate trusted approval.

Generated integrations run outside Trusted Core through typed bounded IPC and
the native Windows containment contract. The canonical executable-package path
uses a capability-free AppContainer, scoped ACLs, explicit handles, and a
pre-resume Job Object; it does not claim VM, dedicated-account, kernel, or
universal same-user filesystem isolation. See
[Windows integration isolation](../security/windows-integration-isolation.md).

CredentialVault owns secret references and uses the Windows secure credential
authority where available. Raw secrets are not ordinary database, log, event,
memory, artifact, prompt or backup data. Data classification and workspace
scope remain enforced for context and retrieval.

UpdatePreview, authenticated recovery/LKG, certification, Shadow/Canary, Golden
Workflow and verification gates are trusted application responsibilities. The
candidate or model cannot rewrite their facts or risk decisions. A complete
signed self-update executor remains outside this candidate's claim.

Opportunity proposals require successful trusted preparation. Acquisition,
preparation, security-blocked, and unknown-outcome failures remain non-ready and
cannot be proposed or accepted, including after restart; the opportunity store
reconciles legacy inconsistent rows fail closed.

## Privacy and local-first behavior

The default application uses local configuration and a local provider endpoint
when configured. Cloud providers, remote approval, external capabilities and
hardware capture are opt-in configuration choices and remain subject to their
provider, privacy and permission policies. JARVIS does not include a mandatory
cloud account or a built-in product integration catalog.

Approved knowledge sources are explicitly scoped; whole-filesystem indexing is
not enabled by default. Backup is separate from LKG recovery and does not
export raw credential secrets or large model caches by default.

## Voice

Voice capture, STT, TTS, wake-word and PTT paths are optional provider-neutral
capabilities. They must degrade to safer modes when unavailable. Speech
recognition alone is not trusted owner identity: privileged/high-risk spoken
approval is not accepted without a separate authenticated owner channel.
Voice can narrate the same trusted PermissionRequest, read details, deny or
cancel, and hand the immutable request to the trusted desktop approval surface.

The default composition reports voice unavailable unless providers are
explicitly composed. Hardware evidence is recorded separately and is not
implied by module or device availability.

## Windows scope

The candidate targets Windows-first operation with exact executable identity,
sanitized launch environment, dedicated integration paths, reduced tokens,
explicit handles, Job Objects, bounded IPC and brokered capability operations.
The real Windows acceptance record documents which UI, camera, audio, browser,
MCP and burn-in checks were actually run:
[v1 Windows acceptance](../v1-windows-acceptance.md).

## Known limitations

The candidate must not be represented as having passed unexecuted hardware or
manual checks. In particular, optional voice output/runtime, browser companion,
configured MCP, cross-machine restore, long-term burn-in, and a
production-owned first-run wizard bootstrap require their own
evidence. The canonical generated executable path has local AppContainer/ACL/
Job evidence, but this is not VM, dedicated-account, kernel, or universal
same-user hostile-code isolation; direct uncomposed process paths remain outside
the claim. Authenticated local recovery/LKG evidence and independent local
adoption identity/provenance evidence are implemented for the declared generic
contracts, while a complete signed self-update executor remains a separate
release gate. The R4 audit and RC preflight determine whether
packaging is authorized.
