## Purpose

This sweep closes the historical semantic false-positive: the original R4
acceptance could reach `ACTIVE` while an unrelated built-in calculator
completed the goal. The current production-composition acceptance uses a
randomized capability and asserts that the generated action itself is selected,
invoked, and independently verified.

The test enters through `ApplicationRuntime.create()` and
`GoalSupervisor.start()` without `RuntimeTestFixture`. It uses only a local
synthetic provider and repository-controlled package process. No donor runtime,
external network, account, or product-specific adapter is used.

## Self-expansion evidence

`tests/test_v1_acceptance.py::test_v1_production_composition_acquires_randomized_capability_and_restores_it`
proves the following for fresh randomized identifiers on every run:

| Check | Evidence |
|---|---|
| Initial gap | The randomized capability is absent from the initial `ToolRegistry`; the built-in tool capability set is captured before acquisition. |

| Planning selection | The final `PlanningEngine` plan has exactly one step, and its tool ID is the generated action ID; it is not any initial built-in tool. |
| Invocation | The generated adapter emits a capability-tool trace event and the acceptance assertion requires at least one generated invocation. |
| Package execution | The local package process returns the input plus a randomized salt; the asserted output contains that exact expected value. |
| Authority | Tool execution uses the composed `ToolRegistry` and `PermissionBroker` path. The test does not grant approval or write ACTIVE directly. |
| Verification | `GoalSupervisor` invokes the application-owned `VerificationEngine`; typed output/evidence and the expected generated criterion are required. |
| Goal linkage | The verified result is attached to the original goal/task trace and completion state. |
| Restart/reuse | A fresh production `ApplicationRuntime.create()` restores the exact package/version/hash, rebuilds the generated adapter, and completes a second randomized input without regeneration. |

The same acceptance test also removes the immutable package before a later
restart and verifies durable quarantine with no registry projection.

## Subsequent lifecycle finding

The immutable candidate audited by R4, `69a39ae5b438d09471fa5f9bda90ead98b8df78c`,
is permanently `R4_NO_GO`. Its acquisition-exception branch persisted
`READY_TO_PROPOSE` together with `preparation_state=FAILED`, and the proposal path
checked only the top-level status. This document's earlier safe-preparation claim
was therefore incomplete for that candidate; it is not rewritten as evidence that
the defect was fixed there. The mutable follow-up adds a durable `FAILED`
transition, centralized state validation, fail-closed proposal/accept checks,
restart reconciliation, and regression coverage. A future release candidate must
carry that new proof and receive fresh exact-SHA gates.
