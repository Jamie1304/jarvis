# Capability acquisition runtime

JARVIS has one application-owned acquisition coordinator:
`CapabilityAcquisitionCoordinator`. It is a lifecycle coordinator, not a task
engine, planner, permission authority, certifier, or verification authority.

## Production service graph

The composition root creates and owns one instance of each service in the
acquisition graph:

```text
GoalSupervisor
  -> CapabilityAcquisitionCoordinator
     -> CapabilityRegistry / CapabilityGapDetector
     -> EnvironmentDiscoveryService (read-only by default)
     -> SolutionDiscovery
     -> CapabilityFactory
     -> PackageReviewer -> PackageCertifier
     -> SetupConductor -> ProvisioningEngine
     -> PackageActivationService -> HotLoadManager
     -> VerificationEngine
```

`GoalSupervisor` owns durable original intent and delegates execution to the
canonical `PlanningEngine` through `TaskController`. The coordinator does not
create plans, execute tasks, or introduce a second control plane.

## Lifecycle contract

The coordinator follows the acquisition order:

```text
gap -> discover -> adopt/reuse -> research -> build (only if needed)
     -> review -> sandbox/certify -> setup/provision
     -> Shadow -> Canary -> Active -> registry refresh -> verify
```

Discovery is evidence only. Existing compatible capabilities are selected by
`CapabilityFactory` before generation or installation. A package generated by
the production `AgentRuntimeCapabilityGenerator` remains inactive until the
existing review, certification, setup/provisioning, activation, and
verification gates all pass. Generation is admitted by the runtime-owned
`ProviderRouter` and configured `ProviderRegistry`, then executed through the
bounded `AgentLoop`; the model receives no broker, vault, lifecycle, or
activation object. Malformed or unavailable model output fails closed.

`ApplicationRuntime.create` in `production` composition owns the
generic implementation path:

```text
ProviderRegistry -> ProviderRouter -> AgentLoop
  -> AgentRuntimeCapabilityGenerator
  -> ProductionPackageStore (hash-addressed package content)
  -> GeneratedPackageReviewer -> PackageCertifier
  -> ProductionSandboxRunner (Windows AppContainer on Windows)
  -> SetupConductor / typed ProvisioningEngine
  -> PackageActivationService / HotLoadManager
  -> trusted Shadow/Canary attestations -> VerificationEngine
```

The package store owns package content, not lifecycle authority.
Certification/activation state remains solely in
`SQLiteCapabilityLifecycleStore`. The generic generated v1 worker is
read-only and communicates through bounded JSON IPC; future effectful packages
must declare typed broker capabilities and cannot use this worker path to
bypass permission policy. If no routable local model/provider is configured,
generation reports `WAITING_FOR_MODEL_PROVIDER`/fails closed rather than using
an unavailable generator or silently activating a package.

The coordinator never:

- approves an action or creates a trusted approval;
- certifies package code;
- promotes a package without `PackageActivationService`;
- accepts model prose as verification;
- bypasses `ToolRegistry -> PermissionBroker -> Policy`;
- turns a discovery observation, setup context, or adoption decision into
  authority.

## Failure, waiting, and restart

The coordinator reports named lifecycle states for review, setup, approval,
Shadow, Canary, verification, and failure. A setup run is owned by
`SetupConductor`; provisioning outcomes are owned by `ProvisioningEngine`;
activation evidence is owned by `PackageActivationService`; and original goal
intent is owned by the durable `GoalSupervisorStore`.

Waiting states therefore resume through the owner of the pending boundary.
Unconfigured build, activation, and verification collectors fail closed rather
than silently installing, activating, or declaring success. A restart
reconciles durable GoalSupervisor, SetupConductor, provisioning, activation,
and planning state before a caller requests another bounded attempt. Unknown
effects are not replayed by this composition layer.

## Reuse and test boundary

The deterministic acceptance suite has two explicit paths. Existing
`RuntimeTestFixture` cases use synthetic package/runtime observations while
still entering through `ApplicationRuntime.create`; they do not represent
production package execution. The production case uses no fixture: a
randomized capability request enters the same composition with a fake provider
registered only through `ProviderRegistry`, then proves generation, review,
AppContainer sandboxing, certification, Setup/Provision boundaries, trusted
Shadow/Canary, ACTIVE registry projection, safe invocation, and restart
restoration. No test directly marks a package ACTIVE or calls a lower-level
factory as a substitute for the production path.

Adding a future capability must not add a product-specific branch to JARVIS
core. It supplies a reviewed package through the generic acquisition contract;
missing provider, sandbox, certification, or typed setup authority remains an
explicit safe waiting/degraded failure.

## Ownership additions

The runtime owns separate durable databases for goal-supervisor state, setup
runs, and trusted effect attestations. These are not alternate task, planning,
permission, or capability stores. The authoritative-state map should be
updated when a future implementation adds durable coordinator-specific state.
